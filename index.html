The vulnerable checker

Simulated C. A wrong-length guess is rejected instantly. A right-length guess sleeps one second per mismatched character, which leaks the Hamming distance to the secret.

int check_password(const char *guess, const char *secret) {
    if (strlen(guess) != strlen(secret))
        return 0;                       /* instant reject */
    int wrong = 0;
    for (size_t i = 0; i < strlen(secret); i++)
        if (guess[i] != secret[i]) wrong++;
    sleep(wrong);                       /* 1 s per mismatch */
    return wrong == 0;
}

Why it breaks, and the fix

The checker leaks two things through time alone. The early return 0 on a length mismatch tells the attacker when the length is right (the only length that sleeps), and the sleep(wrong) turns the response time into a Hamming-distance oracle: it says how many characters are wrong, not just that something is wrong. With that oracle each position can be solved independently. Brute force over an alphabet of 62 symbols would cost about 6211 guesses for an 11-character secret; the oracle brings it down to roughly 24 + 11 × 62 guesses, and the attacker never needs to see the secret, only the clock.

The fix is to make every wrong guess look the same from the outside. A constant-time comparison always walks the full buffer, folds every byte difference into one accumulator with XOR and OR instead of branching or counting, and never sleeps or returns early based on how close the guess was. Comparing fixed-length hashes rather than the raw strings also removes the length leak. Switch on Fixed (constant-time) version above and run Auto-crack again: every probe returns an identical, instant "Access denied", so the attacker has no signal to climb.

Why the pattern explodes

The email group ends with the class [a-zA-Z0-9-.]+ and the next copy of the group starts with [a-zA-Z0-9_.+-]+. Those two classes overlap (letters, digits, dash and dot are in both), so where one block's tail runs straight into the next block's head the engine has several valid ways to decide where the tail stops and the head begins. That ambiguity is a constant number of choices per boundary. The * wrapped around the group is what multiplies them: with n blocks there are n - 1 boundaries, each with k independent splits, so there are about kn-1 distinct parses of the same text. On the benign input the greedy first parse succeeds and the alternatives are never visited. Add one trailing character that cannot match and the full match fails at the very end, so a backtracking engine tries every one of those kn-1 parses before giving up. (a+)+$ is the same shape stripped to the bone: nested repetition over one letter means a run of n a's can be split into inner runs in 2n-1 ways, and the trailing ! rejects every one of them. The mitigations follow directly: remove the overlap (make the classes disjoint or add a separator), avoid nested quantifiers, bound input length, or use a linear-time engine such as RE2 that never backtracks.

Build the list

Simulated Java. Every shape stores its own next, except Rectangle, whose next is static and therefore shared by every Rectangle in the program.

class Rectangle extends Shape {
    static Shape next;                  // one field for ALL rectangles
    void setNext(Shape n) { next = n; }
    Shape getNext()       { return next; }
}
// build(): for (int i = 0; i < 5; i++) nodes[i].setNext(nodes[i + 1]);
// play():  walk from nodes[0] until getNext() == null;
//          a 7th visit throws TimeLimitExceeded

Why one Rectangle is harmless and two can loop

build() calls setNext on slots 1 through 5 in order; slot 6 has no successor, so its next is never written. For a Rectangle, setNext writes the single static field, so the last Rectangle among slots 1 to 5 wins and every Rectangle afterwards answers getNext() with that same node. With exactly one Rectangle the one write is the right one (or, in slot 6, no write happens and next stays null), so the list is intact and traversal is O(n). Put a Rectangle in slot 6 and another one in some earlier slot j, and slot 6 now reports node j + 1, which is behind it: the walk goes j, j + 1, ..., 6, j + 1, ... and never reaches null. That is a guaranteed cycle regardless of the other shapes. Two Rectangles that are both before slot 6 do not loop, but the earlier one points at the later one's successor, so the walk silently skips nodes. Either way, shared mutable state has turned a linear walk into something that depends on what happened to be built last. The fix is to make next an instance field, or better, keep the links inside the list and out of the elements. This page resets the static field before each build so rounds stay independent; in a real JVM it would also carry stale values from the previous round.
